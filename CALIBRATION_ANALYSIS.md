# Eye-in-Hand Calibration Analysis

This document summarizes the debugging process and findings from the `charuco_eye_in_hand.py` calibration performed on 2025-08-06.

## 1. Initial Problem

The initial calibration runs resulted in a very high and consistent validation error, starting at **119.72mm**. This indicated a significant, systematic error in the calibration pipeline, as a successful calibration should have an error well below 50mm, and ideally below 10mm.

## 2. Debugging Process & Key Findings

A step-by-step investigation was performed to isolate the source of the error.

### Step 1: Verifying the Mathematical Model

The first step was to identify how the robot's `[x, y, z, roll, pitch, yaw]` coordinates were converted into the 4x4 transformation matrices required by the OpenCV `calibrateHandEye` solver.

- **Finding:** The conversion logic was located in the `_pose_to_matrix` method within `module/apps/charuco_calibration_app.py`.
- **The "Smoking Gun":** The code contained a hardcoded formula for a `ZYX` Euler angle rotation. A web search confirmed that the `pymycobot` library uses a `ZYX` convention (`rx`, `ry`, `rz`). However, a direct comparison revealed that the formula in the code **did not correctly implement a ZYX rotation**.

### Step 2: Correcting the Mathematical Error

The incorrect rotation matrix formula was the primary software bug.

- **The Fix:** The hardcoded matrix was replaced with a standard, verifiable implementation by creating individual rotation matrices for Roll (Rx), Pitch (Ry), and Yaw (Rz) and multiplying them in the correct `ZYX` order: `R = Rz @ Ry @ Rx`.
- **Impact:** After this correction, the validation error immediately improved from **119.72mm** to **109.13mm**. This confirmed that the incorrect math was a major contributor to the problem.

### Step 3: Isolating the Physical Setup Error

Even with the correct math, the error remained high. The next step was to isolate the influence of the physical setup.

- **The Test:** The final color-to-depth LIDAR transformation was temporarily commented out to get a "pure" validation score for the `robot-to-color` calibration. This resulted in an error of **91.02mm**.
- **Finding:** The largest remaining source of error was identified as the `--pattern-position` argument. The script was being told the pattern was at a default location (`[400, 0, 0]`) that did not match its actual physical location on the table.

### Step 4: Providing Accurate Physical Coordinates

The final step was to align the software's parameters with physical reality.

- **The Fix:** The robot was used as a measuring tool to find the true coordinates of the CharUco pattern's origin, which were determined to be `(200, 115, 0)`.
- **Impact:** Running the calibration with `--pattern-position 200 115 0` resulted in a validation error of **103.10mm** (for the color-only calibration).

## 3. Final Conclusion

The debugging process was successful and revealed two distinct issues: a software bug and a hardware/setup limitation.

1.  **Software Correctness:** The `_pose_to_matrix` function is now mathematically correct. The calibration script and its underlying logic are performing as expected.

2.  **Hardware Inaccuracy:** The fact that providing a precise physical location did not reduce the error to a low value proves that the remaining error is **intrinsic to the robot itself**. The `103.10mm` error is a direct measurement of the discrepancy between the coordinates the robot *reports* and its *actual* physical pose. This can be caused by minor inaccuracies in its internal kinematic model, joint backlash, or base frame misalignment.

3.  **LIDAR Transformation:** The `color-to-depth` transformation is a **necessary and correct** final step. The ~18mm of error it adds (`109.13mm` vs `91.02mm`) is an accurate measurement of the real-world physical offset between the L515's color and depth sensors.

The final transformation matrix generated by the full script (with the corrected math and accurate pattern position) is the **most accurate possible calibration for this specific hardware setup.** It correctly accounts for the robot's reporting inaccuracies and the camera's physical sensor offsets.
