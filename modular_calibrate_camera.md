The `ConfigFactory` is a centralized place for defining and accessing all the configuration presets. It has a large dictionary called `PRESETS` that holds the parameters for different calibration and tracking scenarios.

When `modular_calibrate_camera.py` is run with a specific `--config` argument (e.g., `calibration_standard`), the `ConfigFactory.create_preset()` method is called. This method looks up the preset by name in the `PRESETS` dictionary and creates a configuration object (`BEVConfig` in this case) initialized with the parameters defined for that preset.

Let's break down the `calibration_standard` preset to see how it controls the calibration process:

```python
'calibration_standard': {
    'type': 'bev',
    'config': {
        'clustering_params': {
            'min_cluster_size': 15,
            'max_cluster_size': 200,
            'morphology_kernel_size': 3,
            'window_size': 3
        },
        'roi_params': {
            'x_min': -1.5, 'x_max': 1.5,
            'y_min': 0.05, 'y_max': 0.20,  # Focus on table height
            'z_min': 0.1, 'z_max': 0.8   # Calibration range
        },
        'calibration_positions': [
            [250, 0, 60, 0, 180, 0],
            [180, -100, 60, 0, 180, 0],
            # ... more points
        ],
        'test_positions': [
            [200, -60, 60, 0, 180, 0],
            # ... more points
        ],
        'robot_params': {
            'max_speed': 40,
            # ... other params
        },
        'accuracy_thresholds': {
            'max_calibration_error': 100.0,  # mm
            'max_validation_error': 50.0,    # mm
            'min_calibration_points': 3,
        }
    }
},
```

-   **`clustering_params`**: These directly control the `BEVClusteringStrategy`.
    -   `min_cluster_size` and `max_cluster_size` define the valid size for a detected object in the BEV image, filtering out noise or large surfaces like the table itself.
-   **`roi_params`**: This dictionary defines the 3D Region of Interest.
    -   `y_min` and `y_max` are particularly important as they define the height range (from the camera's perspective) to focus on. This is set to a narrow band around the expected height of the table to ignore points on the floor or ceiling.
-   **`calibration_positions`**: This is the list of `[x, y, z, rx, ry, rz]` coordinates that the robot will move to. The script iterates through this list to collect the calibration data points.
-   **`test_positions`**: After calibration, the robot moves to these points to validate the accuracy of the calculated transformation matrix.
-   **`robot_params`**: Controls the robot's behavior, such as its `max_speed` during calibration movements.
-   **`accuracy_thresholds`**: Defines the acceptable error margins. If the calculated error is higher than `max_validation_error`, the calibration is considered failed.

This configuration-driven approach makes the system highly flexible. To create a new calibration routine (e.g., for a different robot or a different camera setup), you would simply add a new preset to the `ConfigFactory` with the appropriate parameters, without needing to change the core application logic.

This concludes the detailed analysis of the `modular_calibrate_camera.py` script and its dependencies. The system is designed in a modular and extensible way, separating the core logic from the specific parameters of any given calibration task.

## Usage in Object Tracking

The primary consumer of the `camera_robot_transform.npy` file generated by the calibration process is the `modular_track_object.py` script. This application performs real-time object tracking and uses the transformation matrix to command the robot.

### Key Tracking Functionalities:

*   **Transformation Matrix Loading**: The `MyCobotController` is initialized with the path to the `camera_robot_transform.npy` file, loading the matrix to enable coordinate transformations.
*   **Real-time Detection**: The script uses a detection strategy (e.g., `BEVClusteringStrategy`) to find objects in the camera's view in real-time.
*   **Coordinate Transformation**: When an object is detected, its position in the camera's coordinate system is multiplied by the transformation matrix. This converts the camera coordinates into the robot's base coordinate system.
*   **Robot Commanding**: The script sends a command to the robot to point its end-effector at the transformed coordinates of the detected object.
*   **Asynchronous Control**: The system uses an asynchronous command queue, allowing the robot to move without freezing the visualization and detection loop, which is crucial for a responsive real-time system.

In summary, the `modular_track_object.py` script closes the loop: `modular_calibrate_camera.py` establishes the geometric relationship between the camera and the robot, and the tracking script leverages that relationship to enable the robot to interact with objects detected by the camera.

## Core Components

### MyCobotController (`module/robot/mycobot_controller.py`)

This class is the direct interface to the myCobot 280 robot arm. Its key responsibilities include:

*   **Connection**: Establishes and manages the serial connection to the robot.
*   **Safety**: Enforces safety constraints, including workspace boundaries, joint limits, and maximum speed.
*   **Coordinate Transformation**: This is where the `camera_robot_transform.npy` is used. The controller takes camera coordinates, applies the transformation to get robot coordinates, and validates them.
*   **Intelligent Movement**: A critical feature is its ability to handle unreachable targets. If an object is outside the robot's reach, the controller calculates a position on the edge of its workspace in the correct direction, ensuring the robot always points towards the object.
*   **Asynchronous Commands**: It integrates with a command queue to allow for non-blocking robot movements, which is essential for fluid real-time tracking.

### RealSenseManager (`module/sensors/realsense_manager.py`)

The `RealSenseManager` is responsible for acquiring and preparing the sensor data that feeds the entire system.

*   **Data Source**: It can use either a live Intel RealSense camera or a pre-recorded `.bag` file, which is useful for repeatable testing.
*   **Gravity Alignment**: This is a crucial feature for creating a stable and predictable coordinate system. By using the camera's built-in IMU, it determines the direction of gravity and automatically rotates the 3D point cloud data to be level with the ground. This compensates for any physical tilt in the camera's mounting, simplifying all subsequent calculations.
*   **Data Acquisition**: It captures and provides the raw point cloud, color image, and metadata for each frame.
